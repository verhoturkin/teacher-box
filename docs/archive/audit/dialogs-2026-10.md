# Диалоги Teacher Box: инвентаризация и предложение (черновик, 2026-10-25)

Рабочий документ для обсуждения, не закоммичен. После согласования превращается в ADR (рус.),
этапы `docs/PLAN.md` (англ.) и правку §8 `docs/design-system.md`.

Источники M3 — справочники скилла `m3-expressive` (`components/containment.md`: Dialogs,
Bottom sheets, Side sheets; `component-tokens.md`: Dialog). Всё, чего M3 не публикует, помечено
**«наше решение»**.

## 1. Что сейчас есть

Всего модальных поверхностей: **28 `p-dialog`**, **7 `p-drawer`** (из них 1 — навигация),
**~20 вызовов подтверждения** в **12 хостах `<p-confirmdialog>`** с `ConfirmationService`,
объявленным локально в 9 компонентах.

Колонка «Телефон» — как диалог выглядит сейчас на ширине < 600 px: правило в `styles.scss`
делает полноэкранным всё, что не `tb-dialog--short` и не подтверждение.

## 2. Главные проблемы

1. **Нет общего компонента диалога.** Каждый из 28 диалогов сам задаёт атрибуты, футер, сброс,
   ожидание и ошибки; правила §8 соблюдаются выборочно.
2. **Вариант на телефоне выбирается «от противного».** Всё, что не `--short`, — полноэкранное,
   включая просмотр и списки. Ширина и поведение на телефоне смешаны в одном классе.
3. **Полноэкранный вариант не по M3.** У M3 full-screen dialog — шапка 56 dp: ✕ в начале,
   заголовок, подтверждающая текстовая кнопка в конце; у нас — шапка PrimeNG с ✕ в конце и
   растянутые кнопки внизу. Получается гибрид, отличный от компьютерного вида лишь частично.
4. **Один объект — разные контейнеры.** Урок у учителя — диалог (на телефоне full-screen), у
   ученика — bottom sheet / диалог.
5. **Больше двух действий в футере** (`lesson-details`, `to-board`, `system-prompts`) и **нет
   нейтрального выхода** (`request-answer`) — против M3 «максимум два: подтвердить + отменить».
6. **Двойное закрытие.** ✕ в шапке и «Отмена» в футере одновременно; у M3 basic dialog ✕ нет.
7. **Начальный фокус**: §8 требует фокус на заголовке, сделано в 4 из 28; остальные — как решит
   PrimeNG.
8. **Подтверждения**: 9 локальных провайдеров и 12 хостов; внутри диалогов — три разных
   самодельных шага подтверждения.
9. **Потеря данных**: закрытие формы с изменениями без вопроса (M3 требует подтвердить отказ
   от изменений для full-screen dialog).

## 3. Предложение: три вида, один компонент, один подход на всех ширинах

Принцип M3 «диалог меняет вариант с брейкпоинтом» (Dialogs §4): **содержимое и разметка
диалога одни и те же**, ширина экрана меняет только контейнер. Автор диалога выбирает **вид по
содержанию**, а не по экрану.

| Вид | Для чего | Compact (< 600 dp) | Medium и шире |
|---|---|---|---|
| `alert` | подтверждения, одно решение, короткие сообщения, ≤ 1 поля (пароль, ссылка, язык) | basic dialog по центру | basic dialog по центру |
| `form` | ввод ≥ 2 полей, мастера, выбор из списка с поиском | **M3 full-screen dialog**: шапка 56 dp «✕ · Заголовок · Сохранить» | basic dialog: заголовок, контент, футер «Отмена · Действие» |
| `sheet` | объект и его действия (урок, строка «отметьте занятия», код привязки) | modal bottom sheet | basic dialog по центру |

Side sheets (справка, колокольчик, ИИ, проверка) остаются отдельным семейством — они не
диалоги и уже унифицированы.

### 3.1 Правила (в §8 вместо нынешних пунктов)

- **Из M3:** basic dialog — ширина 280–560 dp, углы 28 dp, отступы 24 dp, между заголовком и
  текстом 16 dp, между текстом и кнопками 24 dp, между кнопками 8 dp; surface container high;
  кнопки у конечного края, подтверждающая ближе к краю; **не больше двух действий** (одно —
  только «понятно»); при прокрутке заголовок и кнопки закреплены.
- **Из M3:** full-screen dialog — только compact; шапка 56 dp, ✕ — единственная навигация в
  шапке, подтверждение — текстовая кнопка с ясным глаголом («Создать», «Отправить», не «Готово»);
  кнопку подтверждения не делаем disabled; ошибки полей — inline; закрытие с изменениями —
  basic dialog «Отменить изменения?» поверх.
- **Из M3:** modal bottom sheet — только compact, углы 28 dp сверху, surface container low,
  закрывается скримом, действием внутри и Esc.
- **Наше решение:** у `alert` и `form` на medium+ ✕ в шапке нет (выход — «Отмена», Esc, а у
  `alert` и `sheet` — скрим); у `form` скрим не закрывает (защита данных).
- **Наше решение:** ширины — `normal` 32 rem и `wide` 40 rem (40 rem = 560 dp, максимум M3);
  `alert` — 35 rem. Ширина — отдельный параметр, не связан с телефонным вариантом.
- **Наше решение (пересмотр §8):** начальный фокус — на первом поле у `form` (так велит M3), на
  заголовке у `alert` и `sheet` (чтобы Enter случайно не подтвердил опасное действие).
- Дополнительные действия (третья кнопка, опасные действия) — в ⋮ шапки, как уже у урока.
  Для `to-board` — три способа становятся радио-списком (как язык субтитров) + одно
  «Перенести»; «Сбросить» в `system-prompts` — в ⋮; `request-answer` — «Отмена» + основное
  действие, «Отклонить» — в ⋮ (или выбор «Одобрить / Отклонить» сегментом).
- Ошибка сервера в `form` — над формой (сразу видна), с прокруткой к ней; внутри `alert` — под
  текстом.
- Подтверждение изнутри `form` на compact — настоящий basic dialog поверх (M3 разрешает поверх
  full-screen); на medium+ и внутри `alert`/`sheet` — **общий встроенный шаг** (см. 3.2).

### 3.2 Общий код в `shared/ui`

1. **`<tb-dialog>`** — единственная обёртка над `p-dialog` / `p-drawer`:

   ```html
   <tb-dialog kind="form" width="wide" [(visible)]="visible" [headline]="t.title"
              [form]="form" [state]="submit" [confirmLabel]="c.save">
     <ng-template tbDialogHeaderActions> … ✎, ⋮ … </ng-template>
     <!-- поля формы; <form>, id, tbSubmitFor, Отмена — внутри компонента -->
   </tb-dialog>
   ```

   Берёт на себя: `modal`, `draggable=false`, `appendTo=body`, `blockScroll`, ширину, выбор
   контейнера по `injectWindowSize()`, шапку full-screen на compact, футер «Отмена · Действие»,
   кнопку в состоянии `loading`, показ ошибки, начальный фокус и возврат фокуса (логика
   `ModalDrawer` переезжает сюда), `aria-labelledby`, `role="alertdialog"` для `alert`, вопрос
   «Отменить изменения?» при закрытии грязной формы, запрет закрытия (`[closable]` для стадий
   перезапуска). Для `kind="sheet"` на compact рендерит `p-drawer` bottom с `tb-sheet`.

2. **`dialogSubmit()`** — функция-хелпер вместо `pending`/`error`/`effect`/`subscribe`:

   ```ts
   readonly visible = model(false);
   protected readonly form = inject(NonNullableFormBuilder).group({ … });
   protected readonly submit = dialogSubmit({
     visible: this.visible,
     form: this.form,                      // сбрасывается при открытии
     failed: T.studentForm.failed,
     request: (value) => this.api.createStudent(toRequest(value)),
     done: (created) => this.created.emit(created),   // и закрыть
   });
   ```

   `submit.pending()`, `submit.error()`, `submit.run()`; `<tb-dialog [state]="submit">` сам
   подключает их к кнопке и сообщению. Класс формы-диалога сжимается до полей и `request`.

3. **`Confirm`** — сервис поверх одного `<p-confirmdialog>` в `shell` и одного
   `ConfirmationService` в `app.config.ts`:

   ```ts
   private readonly confirm = inject(Confirm);
   this.confirm.danger({ headline: t.deleteTitle, message: t.deleteText(name), action: t.delete })
     .then((ok) => ok && this.remove(id));
   ```

   Удаляет 9 провайдеров и 12 хостов; `dangerConfirmation`/`safeConfirmation` становятся
   внутренностью сервиса.

4. **`<tb-dialog-confirm-step>`** — встроенный шаг подтверждения внутри `alert`/`sheet` (и `form`
   на medium+): текст + свои две кнопки вместо футера. Заменяет три самодельных варианта
   (`board-backups`, `lesson-details`, `restore-dialog`).

5. **`<tb-dialog-steps>`** (по желанию, позже) — стадии/шаги для `bot-wizard`, `restore-dialog`,
   `settings-page` (общий сценарий «сохранить → перезапуск → войти снова»).

### 3.3 Как разложатся существующие диалоги

| Вид | Диалоги |
|---|---|
| `alert` | все подтверждения; `caption-language`, `invite-link`, `restore-dialog`, `settings-page` (рестарт), `call-stats` |
| `form` | `student-form`, `group-form`, `payment`, `lesson`, `off-time`, `request-answer`, `change-request`, `board`, `textbook`, `bind-textbook`, `assign-more`, `broadcast`, оба AI-промпта, `reset-card`, `attendance`, `to-board`, `bot-wizard`, `call-prejoin` |
| `sheet` | урок учителя (`lesson-details`) и ученика (`my-schedule-page`) — **один подход**, строка `todo-queue`, код мессенджера (`channels-panel`), `board-backups` |

## 4. Поля в формах: filled везде (решено 2026-10-25)

**Сейчас.** По умолчанию — outlined; filled (`.tb-field--filled`, `shared/ui/filled-field.scss`,
0.33.x) только в «Новый ученик» и «Профиль» ученика. Это смешение вариантов между разделами.

**Решение.** Один вариант на всё приложение — **M3 filled text field**: все формы, диалоги,
страницы настроек и профилей. Исключение — поиск: это отдельный компонент M3 (contained search
bar), он остаётся как есть.

- **Из M3:** оба варианта функционально равны, выбор — стиль; нельзя смешивать варианты в одной
  области, в том числе «filled в форме, outlined в диалоге поверх». Геометрия и роли — как уже в
  §10 `design-system.md`: 56 dp, верхние углы 4 dp, нижние прямые, 16 dp по горизонтали;
  контейнер surface container highest, метка on surface variant, активная линия primary.
- **Риск — контраст в диалоге.** Фон диалога — surface container high, поля — surface container
  highest: соседние тона. Граница поля держится в основном на нижней линии. При внедрении —
  визуальная проверка в обеих темах на диалоге, карточке и странице. **Наше решение, если не
  хватит:** не трогать роли M3, а оставить линию 1 dp on surface (как сейчас в
  `filled-field.scss`) — роли и толщину не придумываем сверх этого.
- **Объём.** `filled-field.scss` сейчас обслуживает только нативные `input` / `textarea`. Нужно
  распространить вариант на составные контролы PrimeNG: `p-select`, `p-multiselect`,
  `p-datepicker`, `p-inputnumber`, `p-password`, `p-autocomplete`. В пресете уже есть токены
  `filledBackground` / `filledHoverBackground` / `filledFocusBackground`; глобальный
  `inputVariant: 'filled'` в `providePrimeNG` — проверить по документации PrimeNG 21 (context7)
  перед внедрением.
- **Метка внутри поля.** Filled в M3 — метка внутри контейнера (Body Large пустая, Body Small
  заполненная). Это значит одна разметка поля для всех контролов: `.tb-field` становится
  filled по умолчанию, класс `tb-field--filled` и правила вырезов outlined-меток удаляются.
- **В общем коде.** Вариант задаётся один раз (глобальный стиль `.tb-field` + конфиг PrimeNG),
  ни один диалог не выбирает его сам; `<tb-dialog>` про варианты полей ничего не знает.

## 5. Карточка урока учителя (вид `sheet`)

### 5.1 Что сейчас (`schedule/teacher/lesson-details-dialog.ts`, 643 строки)

- Заголовок всегда «Занятие»; с кем урок — жирной строкой в теле.
- Пять способов показать текст: жирный, обычный `div`, приглушённый `small`, «Тема: …»,
  заявки ученика простым текстом без действия.
- Три вида `p-message` в теле: предупреждение об удалении, пересечение со встроенной кнопкой
  «Всё равно восстановить», ошибка.
- Отмена урока — форма внутри карточки (причина, два флажка), а в **футер** при отмене и
  удалении попадают `p-select` «Только это / Это и следующие» и инфо-`p-message`.
- Футер в шести состояниях: «Закрыть» · «Пропуск | Проведено» · «Отметить посещаемость» ·
  «Восстановить» · «Отмена + Отменить занятие» · «Отмена + Удалить».
- У ученика тот же объект показан другим шаблоном (`my-schedule-page`, `tb-lesson-summary`,
  `tb-lesson-actions`).

### 5.2 Как будет

Компонент содержимого в `schedule/ui` (общий для учителя и ученика) внутри
`<tb-dialog kind="sheet">`: на телефоне — modal bottom sheet, на medium и шире — basic dialog.

1. **Шапка.** Заголовок — с кем урок (имя ученика или название группы). Справа ✎ (только у
   запланированного) и ⋮. Под заголовком — одна метка статуса, только если урок не
   запланирован (как у ученика).
2. **Тело — один сегментированный список `tb-list`**, каждый факт — строка с иконкой:

   | Иконка | Строка | Справа |
   |---|---|---|
   | `schedule` | дата · время; вторая строка «перенесено с …» | — |
   | `topic` | тема | — |
   | `videocam` | комната | тональная «Подключиться» |
   | `dashboard` | доски — чипы | — |
   | `event_busy` | причина отмены (только у отменённого) | — |

   Для прошедшего урока одного ученика в списке есть строка **«Итог»** (иконка `fact_check`)
   с переключателем «Проведено | Пропуск» — **M3 connected button group, single-select, без
   обязательного выбора**:
   - без отметки ничего не выбрано; отмеченный итог — выбранная кнопка (primary, полностью
     круглая), вторая — тональная;
   - нажатие на невыбранный вариант сразу сохраняет итог (кнопка в `[loading]`), как
     переключатель; нажатие на выбранный снимает отметку — пункт ⋮ «Снять отметку» не нужен;
   - ошибка — snackbar, выбор возвращается к прежнему;
   - **из M3:** connected group — для выбора вариантов из переключателей, single-select и
     «selection-required» — опции; на всю ширину поверхности, на широких окнах — с
     максимальной шириной. **Наше решение:** ширина как у строки списка, иконки `check` и
     `person_remove` у вариантов; это тот же элемент, что у участника в `attendance-dialog`.
3. **Группа.** Подзаголовок «Участники» (Title Medium) и тот же `tb-list`: аватар, имя, метка
   посещаемости.
4. **Заявки ученика.** Строка списка в tertiary container (**из M3:** tertiary — малые элементы,
   требующие особого внимания) с кнопкой «Ответить» → существующий диалог ответа на заявку.
5. **Футер — не больше двух действий, одно состояние — одно действие:**

   | Состояние | Действие |
   |---|---|
   | ещё не начался | футера нет (Esc, скрим, ✕ на medium+) |
   | прошёл, один ученик | футера нет — итог переключателем «Итог» в теле |
   | прошёл, группа | «Отметить посещаемость» |
   | отменён | «Восстановить» |

6. **Отмена и удаление — вне карточки** (пункты ⋮):
   - «Отменить занятие…» → отдельный `form`-диалог: причина, «по инициативе ученика»,
     «списать оплату», для серии — радио-список «Только это / Это и следующие» с подсказкой,
     сколько уроков затронет;
   - «Удалить…» → `Confirm.danger`, для серии — тот же радио-список; необратимость — текст
     подтверждения, а не отдельный `p-message`;
   - «Снять отметку» — у урока одного ученика это повторное нажатие выбранного «Итога», пункт
     ⋮ убирается; у группы пункт ⋮ остаётся (в `attendance-dialog` выбор обязателен,
     `allowEmpty=false`, и снять отметку урока там нельзя);
   - пересечение при восстановлении → `Confirm.safe` «Время занято — всё равно восстановить?»
     (как уже `busyHeader` в `schedule-page`).
7. **Ошибки действий** («Проведено» не сохранилось) — snackbar с «Повторить», не блок в
   карточке. **Наше решение** (M3 советует snackbar для сообщений низкой и средней важности).
8. **Ученик** видит тот же список фактов и свои действия («Подключиться», «Перенести |
   Отменить» — заявки), без ✎, ⋮ и отметок. `tb-lesson-summary` и шаблон карточки из
   `my-schedule-page` заменяются общим компонентом.

Итог: в карточке три вида элементов — список, метки, кнопки; ни одного поля ввода; три
встроенных состояния (удаление, отмена, пересечение) становятся стандартными диалогами.

### 5.3 Группы кнопок: выбор и действия

`tb-button-group` сейчас оформлена как **M3 connected button group** (`design-system.md` §7:
внутренние углы 8 px, выбранная — primary и полностью круглая). **Из M3:** connected group —
только для **переключателей** (выбор вариантов, видов, сортировки); «Avoid using a connected
group when none of the buttons can be toggled». Для обычных действий рядом — **standard button
group**: невидимый контейнер с промежутками между кнопками, кнопки не склеены, при нажатии
меняют форму и ширину, соседние на время подстраиваются.

Три места используют connected group для действий — это ошибка, к тому же primary-кнопка в
такой группе читается как «уже выбрано»:

| Где | Сейчас | Станет |
|---|---|---|
| `schedule/teacher/lesson-details-dialog` | «Пропуск \| Проведено» в футере | переключатель «Итог» в теле (§5.2) — connected group по назначению |
| `schedule/ui/lesson-actions` (ученик) | «Перенести \| Отменить» | standard button group: две тональные кнопки |
| `schedule/ui/schedule-agenda` (неотмеченный урок) | «Проведено \| Пропуск» / «Отметить» | standard button group: «Проведено» и «Пропуск» отдельными кнопками |

Правило в `design-system.md` §7 разделяется на два:

- **`tb-button-group--connected`** — только переключатели (`aria-pressed` или
  `p-selectbutton`): «Итог», посещаемость участника, виды календаря `tb-fc-segments`.
- **`tb-button-group`** (standard) — действия рядом. **Из M3:** контейнер облегает кнопки,
  форма меняется при нажатии; промежуток для small-кнопок — 12 dp (Compose-токен
  `ButtonGroupSmall.BetweenSpace`; у connected — 2 dp, `ConnectedButtonGroupSmall`, как у нас
  уже сделано). В футере диалога промежуток остаётся 8 dp («Padding between buttons» диалога).

Альтернатива для повестки (не выбрана): неотмеченный урок показывает тот же переключатель
«Итог» без выбора — один элемент везде. Минус: в строке списка переключатель шире двух кнопок.
