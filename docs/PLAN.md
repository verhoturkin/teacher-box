# План реализации Teacher Box

Пошаговый план. Каждый подэтап завершается зелёным `./scripts/verify.sh` и коммитом
(см. AGENTS.md §8–9). Отмечайте `[x]` в том же коммите, что и код.

Легенда: **B** — backend, **F** — frontend, **D** — docker/инфраструктура.

# Версия 1.1

Цели: расписание с напоминаниями и календарями, работа Telegram из РФ через прокси,
содержательные главные страницы, простой путь учителя в уведомлениях, Gemini, роль
администратора для отладки. Этапы идут в порядке зависимостей: прокси нужен Telegram, ИИ и
Google; главная страница собирается из виджетов расписания, оплат, заданий и уведомлений.

Новые решения: ADR-0008 (расписание и календари), ADR-0009 (настройки интеграций в БД и
исходящий прокси), ADR-0010 (администратор и диагностика); дополнения в ADR-0006 (Gemini)
и ADR-0007 (FullCalendar).

## Этап 11. Исходящий прокси для внешних интеграций

- [x] 11.1 **B** `shared.http.OutboundProxy`: разбор `http://[user:pass@]host:port` и
      `socks5://host:port`, фабрика HTTP-клиента для `RestClient` (JDK `HttpClient` не умеет
      SOCKS — с прокси используется `HttpURLConnection` + `java.net.Proxy`, HTTP/1.1),
      пароль прокси не попадает в логи. Тесты с локальными HTTP- и SOCKS5-прокси.
- [x] 11.2 **B** Telegram через `TEACHERBOX_NOTIFICATIONS_TELEGRAM_PROXY`: long polling и
      отправка; проверка связи (`getMe`) при старте — понятная ошибка в логе и статус в
      «Настройках». VK и MAX всегда ходят напрямую (российские сервисы).
- [x] 11.3 **B** ИИ через `TEACHERBOX_AI_PROXY`: Anthropic SDK (`proxy` + `proxyAuthenticator`)
      и OpenAI-совместимые провайдеры — API Anthropic, OpenAI и Gemini из РФ недоступны.
- [x] 11.4 **D** `extra_hosts: host.docker.internal:host-gateway` в compose; документация:
      прокси на хосте, прокси в соседнем контейнере (xray/sing-box с входом SOCKS5/HTTP),

      VPS). `.env.example`, README, `docs/operations.md`.

## Этап 12. ИИ: Gemini

Итог исследования: **подписку Google AI Pro подключить нельзя.** Её преимущества действуют
только в веб-интерфейсе Google AI Studio; вызовы Gemini API из приложений оплачиваются
отдельно; использование OAuth-токенов Gemini CLI сторонними программами нарушает условия
Google (с февраля 2026 — блокировка аккаунтов, в том числе платных). Официального способа
для сторонних приложений нет. Законный путь — ключ Gemini API из Google AI Studio
(бесплатный уровень с лимитами или оплата по токенам).

- [x] 12.1 **B** Провайдер `gemini`: пресет OpenAI-совместимого адаптера
      (`https://generativelanguage.googleapis.com/v1beta/openai/`, модель по умолчанию —
      `gemini-3.8-flash`), проверка structured outputs на схемах черновиков и причин отказа
      (safety → `ai.refused`); если совместимый endpoint не справляется со схемами — отдельный
      адаптер на официальном Java SDK `google-genai`. Тесты на локальном HTTP-сервере.
- [x] 12.2 **F/D** Провайдер и модель на странице «ИИ»; README: получение ключа, недоступность
      в РФ (→ `TEACHERBOX_AI_PROXY`), лимиты бесплатного уровня и то, что на бесплатном уровне
      Google может использовать тексты запросов (ответы учеников) для улучшения своих продуктов.

## Этап 13. Модуль расписания (`schedule`) — backend

- [x] 13.1 **B** ADR-0008, модуль `schedule` (зависит от `shared`, `identity::api`), схема
      `schedule`: `series`, `lessons`, `change_requests`, `feeds`; таблица зависимостей в
      AGENTS.md (`billing` и `notifications` получают `schedule::api` — только события).
- [x] 13.2 **B** Домен: занятие (ученик, начало, длительность, тема, ссылка на онлайн-урок;

      создаются на 12 недель вперёд и продлеваются ночью, изменение серии «с этой даты»,
      предупреждение о пересечении занятий.
- [x] 13.3 **B** Перенос и отмена: учитель — сразу; ученик — запрос (перенос на предложенное

- [x] 13.4 **B** Итог занятия «Проведено» / «Пропуск» → событие → `billing` записывает занятие

- [x] 13.5 **B** События `LessonScheduled`, `LessonRescheduled`, `ScheduledLessonCancelled`,
      `LessonCompleted`, `ChangeRequested`, `ChangeRequestResolved`; напоминания
      `LessonStartingSoon` за интервалы `TEACHERBOX_SCHEDULE_REMINDERS` (по умолчанию
      `PT24H,PT1H`), по одному на интервал.
- [x] 13.6 **B** REST: `/api/teacher/schedule/**` (занятия за период, занятия и серии,
      итоги, запросы), `/api/me/schedule/**` (свои занятия, запросы); тесты «чужой ученик →

- [x] 13.7 **B** Подписка на календарь (ICS, RFC 5545) по секретной ссылке

# Версия 1.2

Цели: групповые занятия, видеовстречи в Яндекс Телемосте, доски Холста у учеников и групп,
работа через ботов для учеников и учителя, справка по приложению. Этапы идут в порядке
зависимостей: группы нужны расписанию, встречам и доскам; основа диалогов в ботах — до
действий модулей; справка пишется последней, когда интерфейс устоялся.

Итоги исследования:

- **Яндекс Телемост.** API (`https://cloud-api.yandex.net/v1/telemost-api`, OAuth-токен
  Яндекс ID со scope `telemost-api:conferences.*`) доступен только пользователям Яндекс 360
  для бизнеса с аккаунтом на домене организации. С личным аккаунтом ссылка встречи создаётся в
  Телемосте вручную. Приложение для ПК открывается ссылкой
  `telemost://https://telemost.yandex.ru/j/<номер>` — так его открывает сам веб-клиент
  Телемоста. Схема не документирована, поэтому рядом всегда есть обычная ссылка (её страница
  тоже предлагает открыть приложение).
- **Холст.** Публичный API (персональные токены) даёт только чтение журнала аудита
  организаций, API для досок нет. Доски умеет менять только локальный MCP-сервер (бета)
  приложения Холст для ПК (`127.0.0.1:47641`), с сервера портала он недоступен. Поэтому в 1.2 —
  доски по ссылкам и перенос материалов через буфер обмена; автоматизация — когда у Холста
  появится серверный API.

Решения: Телемост — оба режима (API для Яндекс 360 для бизнеса и ссылка, вставленная
вручную); постоянная комната у ученика и у группы (в отдельном занятии ссылку можно
заменить); у группы своя цена занятия; Холст — ссылки и копирование.

Новые решения: ADR-0011 (группы и групповые занятия), ADR-0012 (видеовстречи и доски),
ADR-0013 (диалоги с ботами).

# Версия 1.3

Цели: простая первоначальная настройка и знакомство с порталом, название и адрес портала в
настройках, восстановление резервных копий из интерфейса и полный сброс данных с копией перед
ним. Этапы идут в порядке зависимостей: мастеру первоначальной настройки нужны название и адрес;
подтверждение паролем и пометки копий нужны и восстановлению, и сбросу; после сброса снова
открывается первоначальная настройка.

Итоги исследования:

- **Адрес портала.** Ссылки сейчас собираются из разных мест. Ссылки в сообщениях мессенджеров и
  ссылка на справку в боте берутся из `TEACHERBOX_PUBLIC_URL`; если он не задан, ссылок нет.
  Ссылка-приглашение, адрес подписки на календарь и адреса возврата для Google и Яндекса берутся
  из адреса, по которому открыт браузер. Если учитель открыл портал по адресу домашней сети,
  ученик получит ссылку, которая у него не откроется.
- **Название.** «Teacher Box» зашито в шапку, вкладку браузера, страницу входа и название
  календаря в подписке ICS.
- **Первый запуск.** Учётная запись учителя создаётся из переменных окружения. Если пароль не
  задан, он создаётся случайно и печатается в журнал сервера, а журнал читает администратор
  (поиск по журналу, ADR-0010). Имя учителя («Учитель» по умолчанию) и цену занятия по умолчанию
  в интерфейсе не поменять.
- **Резервные копии.** Создавать, скачивать и удалять их может только учитель. Восстановить
  копию можно только через каталог `/data/restore/` и перезапуск: копия применяется при запуске,
  до открытия базы, а при ошибке прежние данные возвращаются. Восстанавливать без перезапуска
  пришлось бы с остановкой всех фоновых задач и повторными миграциями, поэтому перезапуск
  надёжнее; контейнер поднимается сам (`restart: unless-stopped` в обоих вариантах compose).
  Сейчас при ошибке восстановления портал не запускается, архив остаётся в `restore/`, и
  контейнер перезапускается по кругу.
- **Сброс.** Данные лежат в схемах модулей, а `platform` о них не знает. Поэтому очищает данные
  каждый модуль сам, через SPI в `shared`, как в проверках интеграций и действиях ботов.

Решения:

- После полного сброса остаются учётные записи учителя и администратора (с паролями) и
  резервные копии. Всё остальное удаляется, в том числе подключения, название и адрес портала,
  и снова открывается первоначальная настройка.
- Восстанавливают копию и администратор, и учитель: администратора может не быть.
- Администратор не скачивает копии: в них данные учеников (ADR-0010).
- Адрес из `TEACHERBOX_PUBLIC_URL`, если он задан, важнее адреса из интерфейса, как ключи
  Google и Яндекса.

Новое решение: ADR-0014 (настройки портала, первоначальная настройка, восстановление и сброс).

# Версия 1.4

Цели: редизайн и улучшение UX/UI на компьютере и телефоне, свой логотип портала, закреплённая
шапка, упрощение кода фронтенда и тестов. Этапы идут так, чтобы следующие строились на
предыдущих: сначала чистим код и форматирование (дальнейшие изменения — на чистой базе), затем
дизайн-система (сетка, токены, темы), затем каркас приложения (шапка, нижняя панель), затем
мобильные экраны и главная, в конце — справка и выпуск.

Итоги разбора (компьютер 1366 px и телефон 375 px):

- **Телефон.** Меню пользователя в шапке обрезано у правого края. Таблицы (ученики, оплаты,
  задания) прокручиваются по горизонтали, кнопки действий в строке ученика не видны. Недельная
  сетка расписания нечитаема (7 колонок по ~40 px). Кнопки страниц переносятся в несколько строк,
  четыре карточки сводки «Оплат» занимают весь экран до списка. Шапка уезжает при прокрутке.
- **Компьютер.** Узкий контент и много пустого места; пустые разделы обрываются без подсказки.
  На главной сверху «С чего начать» с зачёркнутыми пунктами, «Сегодня» ниже; нет быстрых
  действий (оплату записывают только из раздела «Оплаты»).
- **Единообразие.** Отступы, радиусы, размеры кнопок и заголовков карточек заданы по месту в
  ~50 компонентах; одни кнопки маленькие, другие обычные, ссылки то подчёркнуты, то нет.
- **Код.** 186 файлов (~19 тыс. строк) и 122 теста (~11 тыс. строк). Одинаковая настройка
  TestBed в 63 тестах, работа с `localStorage` повторяется в 4 местах, стили строк таблиц — в
  нескольких компонентах; часть файлов не отформатирована.
- **Название портала** меняется с версии 1.3 («Настройки» → «Портал»); в 1.4 к нему добавляется
  свой логотип.

Новое решение: ADR-0015 (дизайн-система и мобильный интерфейс).

Решения: на телефоне — нижняя панель разделов, карточки вместо таблиц, расписание списком по
дням, диалоги на весь экран; дизайн по сетке 4/8 px с едиными радиусами, кнопками и
типографикой; шире контент на больших экранах; переключатель темы (светлая, тёмная, как в
системе); цвет портала и свой логотип в настройках; понятные пустые состояния; на главной —
быстрые действия, ближайшее занятие сверху и компактное «С чего начать». Рефакторинг: удаление
мёртвого кода (knip), общие помощники тестов, единое форматирование Prettier с проверкой.
