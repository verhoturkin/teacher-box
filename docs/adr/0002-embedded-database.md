# ADR-0002. Встраиваемая БД: H2 в файловом режиме, схема на модуль

- Статус: принято
- Дата: 2026-09-25

## Контекст

Нужна встраиваемая (embedded) БД с хранением в файловой системе: без отдельного сервера,
данные в volume `/data`, простой бэкап. Нагрузка — единицы одновременных пользователей.
Требование изоляции подсистем (ADR-0001) желательно поддержать и на уровне данных.

## Рассмотренные варианты

| Критерий | H2 2.x (file) | SQLite (xerial) | HSQLDB | Apache Derby |
|---|---|---|---|---|
| Чистая Java, без native-библиотек | да | нет (JNI, разные образы glibc/musl) | да | да |
| Схемы (namespace на модуль) | да | нет (только ATTACH отдельных файлов) | да | да |
| Поддержка в Spring Boot / Flyway / Modulith | полная, в т.ч. Event Registry | частичная (community dialect, нет схем в Modulith registry) | полная | ограниченная |
| Конкурентная запись | MVCC, построчные блокировки | один писатель (WAL) | MVCC | да |
| Онлайн-бэкап | `BACKUP TO 'file.zip'` | backup API / `VACUUM INTO` | `BACKUP DATABASE` | есть |
| Путь миграции на PostgreSQL | стандартный SQL, схемы как в PostgreSQL | нет схем, свой диалект | частично | нет |
| Статус проекта | активно развивается | активно | активно | переведён в архив (2025) |

SQLite обладает самым стабильным форматом файла, но для Java-стека требует native-драйвера,
community-диалекта и не даёт схем — изоляцию данных пришлось бы строить на отдельных файлах
с несколькими `DataSource` и без атомарности между ними. Derby выведен из активной разработки.

## Решение

**H2 2.x в файловом режиме** (`jdbc:h2:file:/data/db/teacherbox`), версия управляется
Spring Boot.

> С 0.10.0 — `jdbc:h2:async:/data/db/teacherbox`: те же файлы, но доступ через `AsynchronousFileChannel`.
> С `file:` прерывание потока (`Thread.interrupt()`) во время чтения или записи файла закрывает его канал,
> MVStore считает это фатальной ошибкой и закрывает базу для всех соединений («The database has been
> closed»); `async:` прерываниям не подвержен. Код портала к тому же не прерывает потоки, работающие с базой.

- **Схема на модуль:** `identity`, `billing`, `homework`, `notifications`, `ai`.
  Каждый модуль имеет свои Flyway-миграции (`db/migration/<module>`) и свою таблицу
  истории миграций внутри своей схемы. Запросы к чужим схемам запрещены (AGENTS.md §4.2).
- Один `DataSource` и один менеджер транзакций — событие публикуется атомарно с изменением
  данных (Event Publication Registry в той же БД).
- Доступ к данным — `JdbcClient` с явным SQL и схемными префиксами (`billing.payments`), без
  кавычек в идентификаторах (H2 приводит их к верхнему регистру, Flyway получает имя схемы
  в верхнем регистре). ORM не используется: SQL прозрачен и проверяется тестом изоляции схем.
- Параметры: `DB_CLOSE_ON_EXIT=FALSE` — закрытие БД выполняет graceful shutdown Spring.
- Надёжность: ежедневный онлайн-бэкап `BACKUP TO` с ротацией (этап 9 плана),
  `stop_grace_period` в compose, чтобы БД корректно закрывалась.
- H2 Console в prod выключена.

## Последствия

- (+) Ноль внешних зависимостей, один файл БД в volume, образ на чистой JRE.
- (+) Изоляция данных модулей на уровне схем при сохранении транзакционности.
- (+) SQL пишется на стандартном подмножестве, схемы совпадают по смыслу со схемами PostgreSQL —
  при росте переход на PostgreSQL сводится к смене драйвера, URL и точечной правке миграций.
- (−) Формат файла H2 может меняться между мажорными версиями — обновление H2 делается только
  через проверенный сценарий «бэкап SQL-скриптом → восстановление» (описать в README при обновлении).
