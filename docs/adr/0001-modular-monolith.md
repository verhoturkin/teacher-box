# ADR-0001. Модульный монолит на Spring Modulith

- Статус: принято
- Дата: 2026-09-25

## Контекст

Требуется высокая изоляция пяти подсистем (аутентификация, оплата, ДЗ, уведомления, ИИ).
При этом продукт self-hosted: один учитель, десятки учеников, установка «одной командой»
на домашний сервер/NAS/VPS с 1–2 ГБ RAM. Нужен и вариант «один контейнер».

## Рассмотренные варианты

1. **Микросервисы** — максимальная изоляция, но 5+ JVM, брокер сообщений, сетевые отказы,
   распределённые транзакции. Для одного учителя — избыточно по ресурсам и сложности,
   и несовместимо с вариантом «один контейнер».
2. **Классический монолит (слои)** — просто, но изоляция держится на дисциплине и быстро деградирует.
3. **Модульный монолит (Spring Modulith)** — один процесс, но границы модулей проверяются
   автоматически, взаимодействие — через публичные API и события.

## Решение

Вариант 3. Каждый бизнес-модуль — пакет верхнего уровня `ru.teacherbox.<module>`:

- публичный контракт — только подпакет `api` (`@NamedInterface`);
- разрешённые зависимости явно указаны в `@ApplicationModule(allowedDependencies)`;
- межмодульные побочные эффекты — через доменные события (`@ApplicationModuleListener`),
  с Event Publication Registry (JDBC) для гарантированной доставки после рестарта;
- собственная схема БД на модуль (см. ADR-0002), без внешних ключей и JOIN между схемами;
- `ApplicationModules.verify()` и ArchUnit в тестах — нарушение границ ломает сборку;
- `@ApplicationModuleTest` поднимает модуль изолированно.

## Последствия

- (+) Любой модуль можно позже вынести в отдельный сервис: контракт и данные уже изолированы.
- (+) Низкие требования к ресурсам, одна JVM.
- (−) Нет физической изоляции отказов: ошибка в модуле может повлиять на процесс
  (смягчается асинхронной обработкой событий и отдельными пулами для внешних интеграций).
- (−) Нужна дисциплина по событиям и фасадам — обеспечивается тестами.
